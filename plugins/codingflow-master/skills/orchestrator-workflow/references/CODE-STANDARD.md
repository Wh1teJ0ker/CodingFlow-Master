# CODE-STANDARD — 前后端通用代码规范

> 技术栈无关的通用代码规范。适用于所有项目的前端、后端、CLI、桌面应用等。目标是保证**高内聚、低耦合**，避免冗余描述，提高代码质量。
>
> Coder 子 Agent 在实施任务时遵守本规范；Reviewer 子 Agent 在审查任务时以此为检查依据之一。

## 1. 分层架构

### 规则

- **三层分离**：Presentation（UI / API 入口）→ Business（业务逻辑）→ Data（数据访问）
- **依赖方向单向**：Presentation → Business → Data，禁止反向依赖
- **禁止跨层调用**：Presentation 不能直接调 Data，必须经过 Business 层
- 每层的职责边界必须清晰，不能混层

### 检查方式

- 审查 import / require / use 关系，是否存在反向依赖
- 检查 Presentation 层是否直接操作数据源（SQL / ORM / fetch localStorage 等）
- 检查 Data 层是否包含业务判断逻辑

### 反例

```text
- 前端组件直接 fetch 后端 API 并处理业务逻辑
- 后端 Controller 直接写 SQL 查询
- Data 层返回原始数据，由 Presentation 层做业务转换
```

## 2. 模块职责

### 规则

- **单一职责**：每个模块 / 文件 / 类 / 函数只做一件事，一句话能描述其作用
- **单文件建议 ≤ 300 行**（不含注释 / 空行），超过必须拆分
- **禁止循环依赖**：A 依赖 B 时，B 不能依赖 A
- 模块对外只暴露必要的接口，内部实现细节不对外可见

### 检查方式

- 读文件第一段注释 / 文件名，能否一句话说清它做什么
- 统计文件行数
- 画依赖图，检查是否有环

### 反例

```text
- 一个 utils.js 里塞了日期格式化、HTTP 请求、本地存储、UI 辅助等不相关功能
- A.ts imports B.ts，B.ts imports A.ts
- 一个 800 行的组件文件包含表单、列表、弹窗、网络请求
```

## 3. 接口契约

### 规则

- 模块间通信通过**明确定义的接口**（函数签名 / 类型定义 / 协议描述）
- 接口必须声明：输入类型、输出类型、错误类型
- **禁止 `any` / 动态类型逃逸**（除非语言本身不支持类型系统）
- 接口变更必须考虑向后兼容，或明确标注为 breaking change

### 检查方式

- 检查函数签名是否有完整类型标注
- 搜索 `any` / `object` / `dict` 等宽泛类型的使用
- 检查 API 接口是否有文档或 schema 定义

### 反例

```text
- 函数参数类型为 any 或未标注
- API 返回 { code, data, message } 但 data 的结构未定义
- 模块直接依赖另一个模块的内部实现而非公开接口
```

## 4. 前端规范

### 规则

- **组件单一职责**：一个组件只做一件事。容器组件负责数据获取和状态管理，展示组件负责渲染
- **状态管理边界明确**：
  - 组件内状态（UI 状态、表单临时态）用组件局部 state
  - 跨组件共享状态（用户信息、全局配置）用全局状态管理（Context / Store / Redux 等）
  - 禁止把全局状态塞进组件局部 state
- **禁止冗余描述**：
  - UI 文案只描述用户可感知的行为，不描述技术实现细节
  - 不在界面上暴露技术术语（如 "API 调用失败" 应改为 "数据加载失败，请重试"）
  - 不在注释中重复代码已清晰表达的信息
- **样式与逻辑分离**：除非 CSS-in-JS 是项目约定，否则样式应独立于组件逻辑
- **禁止内联魔法值**：颜色、尺寸、文案等应抽为常量或配置

### 检查方式

- 组件行数是否超过 200 行
- 是否有展示组件直接调用 API
- 是否有 UI 文案包含技术术语
- 是否有硬编码的魔法值

### 反例

```text
- 一个表单组件既负责渲染又负责 API 调用又负责全局状态管理
- 错误提示写 "TypeError: Cannot read property 'x' of undefined"
- 按钮颜色直接写 #1890ff 而非引用 theme.primaryColor
```

## 5. 后端规范

### 规则

- **服务职责单一**：一个服务类 / 模块只负责一个业务领域
- **错误处理边界明确**：
  - 每层定义自己的错误类型，不透传底层错误到上层
  - Data 层错误（如数据库异常）应在 Business 层转为业务异常
  - Business 层异常应在 Presentation 层转为用户可理解的响应
- **输入验证在入口层完成**：Controller / API handler 层验证输入格式和合法性，Business 层假设输入已验证
- **数据库操作集中在 Data 层**：不在 Business 层写 SQL / ORM 调用
- **事务边界在 Business 层**：跨多个 Data 操作的事务由 Business 层管理

### 检查方式

- 检查 Controller 是否包含业务逻辑
- 检查 Service 是否直接操作数据库
- 检查错误是否被原样透传到 API 响应
- 检查输入验证是否在入口层

### 反例

```text
- Controller 里写 if (user.age < 18) throw ... 业务判断
- Service 里直接写 db.query("SELECT ...")
- API 返回 { error: "ECONNREFUSED 127.0.0.1:5432" } 透传数据库错误
```

## 6. 命名约定

### 规则

- **语义优先**：名字表达意图，不缩写（除非是领域通用术语如 `auth`、`cfg`）
- **一致性**：同一概念在项目内只用一个词（不能同时用 `user` 和 `account` 指代同一实体）
- **文件名 = 默认导出名**（或主要类型名）：`UserService.ts` 导出 `UserService`
- **布尔值用 is/has/can/should 前缀**：`isLoading`、`hasPermission`
- **事件处理用 on/handle 前缀**：`onClick`、`handleSubmit`
- **常量用全大写下划线**：`MAX_RETRY_COUNT`

### 检查方式

- 搜索同一概念是否有多个命名
- 检查布尔值命名是否有 is/has/can/should 前缀
- 检查文件名与导出名是否一致

### 反例

```text
- function proc(req) — 缩写，应为 processRequest
- 同一项目里 user 和 account 混用
- 文件名 user-service.ts 但导出 class UserMgr
```

## 7. 错误处理

### 规则

- **错误必须被处理**，不允许静默吞掉（`catch` 空块禁止）
- **错误信息面向调用者**：包含上下文 + 可操作的建议
- **可预期错误（业务异常）vs 不可预期错误（系统异常）分开处理**：
  - 业务异常：用领域特定错误类型，返回用户可理解的提示
  - 系统异常：记录完整堆栈，返回通用错误提示，不暴露内部细节
- **错误日志包含足够上下文**：操作名称、输入参数摘要、错误堆栈
- **禁止用错误码做控制流**（如 `try { ... } catch { return null }` 来判断条件）

### 检查方式

- 搜索空 catch 块
- 检查错误响应是否包含技术细节
- 检查业务异常和系统异常是否混在一起处理

### 反例

```text
- catch (e) {} — 静默吞掉错误
- catch (e) { return null } — 用错误做控制流
- API 返回 { error: e.stack } — 暴露内部堆栈
- 把 "用户不存在"（业务异常）和 "数据库连接失败"（系统异常）用同一个 catch 处理
```

## 检查清单（Reviewer 参考）

Reviewer 审查任务时，对照以下清单检查代码质量：

- [ ] 分层架构：依赖方向正确，无跨层调用
- [ ] 模块职责：单一职责，无循环依赖，文件行数合理
- [ ] 接口契约：类型完整，无 any 逃逸
- [ ] 前端规范（如适用）：组件职责清晰，状态边界明确，无冗余 UI 描述
- [ ] 后端规范（如适用）：服务职责单一，错误边界明确，输入验证在入口层
- [ ] 命名约定：语义清晰，项目内一致
- [ ] 错误处理：无静默吞错，业务异常与系统异常分开

> 以上清单不全过则不能 `review_passed`，除非任务明确不涉及某项（如纯文档任务不涉及前后端规范）。
