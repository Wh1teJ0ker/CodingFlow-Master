# 00 — Phase 0: 仓库状态判断与文档规划

> 本过程文件定义 Phase 0 的全部逻辑。主会话在进入工作流的第一步阅读本文件，判断仓库状态并执行对应分支。

## 核心原则

Phase 0 是整个工作流的入口。在拆任务之前，必须先回答一个问题：**当前仓库是空的还是非空的？** 这决定了后续所有文档和任务的起点。

- **空仓库** → 从零规划 `docs/` 文档体系，基于用户任务描述建立需求、设计、任务清单。
- **非空仓库** → 先审计现有项目，理解代码结构和已有文档，再构建或规范化 `docs/`。

不允许跳过 Phase 0 直接拆任务。没有文档基线，任务拆分就没有可验收的依据。

## Step 1 — 仓库状态检测

主会话检测当前仓库的实际状态：

1. **检查是否有tracked文件**：`git ls-files` 是否返回空
2. **检查是否有 `docs/` 目录**：是否存在且包含实质内容（不是空目录或只有 `.gitkeep`）
3. **检查是否有 `README.md`**：项目根目录是否存在且有实质内容

判定规则：

| 条件 | 判定 | 进入 |
|------|------|------|
| 无 tracked 文件，或仅有 `.gitignore` / `.gitkeep` / LICENSE 等骨架文件 | **空仓库** | Branch A |
| 有 tracked 源代码文件，或已有 `docs/` 且有实质内容 | **非空仓库** | Branch B |
| 有 tracked 文件但全是文档无代码 | **文档-only 仓库** | 按 Branch A 处理（补全代码文档体系），但保留已有文档 |

## Step 2 — Branch A: 空仓库 → 文档规划

### A.1 确认需求边界

从用户任务描述中提取：
- 项目目标：一句话能说清这个项目做什么
- MVP 范围：当前版本/第一期必须实现什么
- 非目标：明确不做什么
- 验收标准：怎样才算完成

如果用户说"当前需求就是 MVP"，在所有文档中写清"当前文档中的需求默认即本项目第一期 MVP 范围"。

### A.2 建立文档体系

在 `docs/` 下创建以下文档（编号即文件名前缀）：

```text
docs/
├── 00-需求文档.md           # 全景需求、MVP 边界、验收标准
├── 01-页面与交互说明.md      # 全局页面结构、状态流、交互规则（前端项目适用）
├── 02-技术设计文档.md        # 总技术架构、模块职责、关键数据流
├── 03-开发任务清单.md        # 全局任务清单、阶段、依赖、验收方式
├── 04-版本标准.md           # 版本号语义、里程碑索引、版本状态口径
├── versions/
│   └── <ver>/
│       ├── 规划需求.md       # 本版本范围、目标、任务清单
│       ├── 技术方案.md       # 本版本技术方案（简单版本可选）
│       ├── 更新日志.md       # 本版本进度表；必须与 handoff/TASK-BOARD.md 对齐
│       └── release.md       # 本版本发布文档（What's New / Fixed / Downloads）
└── qa/
    └── versions/
        └── <ver>/
            └── QA-审计报告.md # 本版本发布前全局审计报告
```

同时，**项目根目录必须提供双语 README**：
- `README.md`（中文主版）
- `README_EN.md`（英文版）

README 按"轻量仓库入口文档"编写，重点写项目介绍、当前状态、Quick Start、基本验证和必要链接。编写依据见 [`references/README-STANDARD.md`](../references/README-STANDARD.md)，可从 `../../assets/templates/README.md.template` 与 `../../assets/templates/README_EN.md.template` 复制后填充。

版本文档模板可从 `../../assets/templates/` 复制后填充。

### A.3 四份核心文档的职责边界

#### 1. 需求文档（00-需求文档.md）

回答：这个项目要做什么？当前版本先做什么？明确不做什么？核心功能有哪些？验收标准是什么？

必须强调边界：
- 项目目标
- MVP 范围
- 非目标 / 本期不做
- 功能需求
- 非功能需求
- 验收标准

#### 2. 页面与交互说明（01-页面与交互说明.md）

回答：界面有哪些区域？每个按钮或入口做什么？页面状态怎么切换？用户主流程是什么？异常和确认动作怎么处理？

不是视觉稿说明，而是交互行为说明。优先覆盖：页面分区、工具栏/侧栏/主内容区/状态栏、空状态/加载状态/错误状态/未保存状态、主流程。

> 如果是纯后端项目或无 UI 的 CLI/工具项目，本文件可替换为 `01-接口与交互说明.md`，描述 API 接口或 CLI 命令的输入输出行为。

#### 3. 技术设计文档（02-技术设计文档.md）

回答：为什么这么分层？各模块怎么分工？状态如何组织？关键数据结构是什么？核心命令、接口、数据流是什么？性能和错误处理大方向是什么？

优先写清：架构分层、模块职责、数据模型、状态结构、命令/接口、关键数据流、性能策略、错误处理与边界。

> 前后端代码规范见 [`references/CODE-STANDARD.md`](../references/CODE-STANDARD.md)。

#### 4. 开发任务清单（03-开发任务清单.md）

回答：实现时先做什么、后做什么？哪些任务相互依赖？每个任务完成后怎么验证？阶段性里程碑怎么定义？

必须可执行，不能只是泛泛 checklist。优先拆出：阶段划分、任务目标、前置依赖、建议修改位置、实现要点、交付物、验收标准、验证方式、风险点。

> 这份清单是 Phase 1 任务 DAG 拆分的输入源，不是最终交付物。Phase 1 会基于此构建 `handoff/TASK-BOARD.md`。

### A.4 版本化文档

当项目需要分版本/里程碑交付时，`04-版本标准.md` 定义版本号语义（SemVer）、里程碑索引和版本状态口径。每个版本在 `versions/<ver>/` 下有独立的规划需求、技术方案、更新日志和 release.md。

**关键规则**：
- `versions/<ver>/更新日志.md` 的进度表必须与 `handoff/TASK-BOARD.md` 的任务状态保持一致
- 每个 `versions/<ver>/` 必须同步规划对应的 `qa/versions/<ver>/QA-审计报告.md`
- 版本完成/发布状态只能在该 QA 报告已落盘且结论为 `qa_passed` 后写入
- `release.md` 在版本 `qa_passed` 且用户显式指令 tag 后生成

详见 [`06-progress-sync.md`](../sync/06-progress-sync.md) 与 [`07-release-qa-audit.md`](./07-release-qa-audit.md)。

### A.5 完成后

Branch A 完成后，`docs/` 文档体系就绪，进入 **Phase 1**（[`01-task-decomposition.md`](./01-task-decomposition.md)）基于 `03-开发任务清单.md` 拆分任务 DAG。

## Step 3 — Branch B: 非空仓库 → 审计 + 规范化

### B.1 审计现有项目

主会话必须基于实际文件和命令输出审计，不基于对话记忆：

1. **代码结构审计**：
   - 读取项目根目录结构（`ls -la` 或等价操作）
   - 识别技术栈（读取项目清单文件、构建配置等）
   - 识别源代码目录布局（`src/` / `app/` 等）
   - 识别测试结构
   - 识别 CI/构建配置

2. **已有文档审计**：
   - 检查 `docs/` 是否存在，内容是否与代码一致
   - 检查 `README.md` 是否存在，是否反映项目真实状态
   - 检查是否有版本管理文档（`04-版本标准.md`、`versions/` 等）
   - 检查是否有 QA 报告历史

3. **Git 历史审计**：
   - 查看最近提交（`git log --oneline -20`）
   - 识别当前分支和版本 tag（`git tag`）
   - 判断项目处于什么阶段（初始开发 / 功能迭代 / 维护）

4. **代码质量速览**：
   - 扫描模块边界是否清晰
   - 是否有明显的循环依赖或跨层调用
   - 错误处理是否系统化
   - 参考 [`references/CODE-STANDARD.md`](../references/CODE-STANDARD.md) 的规范项

### B.2 构建或规范化 `docs/`

根据审计结果，分三种情况：

#### 情况 1：`docs/` 不存在或为空

按照 Branch A 的文档体系从零创建，但内容必须基于**审计结果**而非用户描述：
- `00-需求文档.md`：从代码和 README 反推实际需求
- `02-技术设计文档.md`：从代码结构反推实际架构
- `03-开发任务清单.md`：基于当前代码状态和用户新任务规划下一步
- 其余文档同理

#### 情况 2：`docs/` 存在但不完整或不一致

- 补全缺失文档
- 修正与代码不一致的描述
- 补充版本化文档体系（如缺失）
- 确保 `versions/<ver>/更新日志.md` 与实际代码进度一致

#### 情况 3：`docs/` 完整且一致

- 仅做增量更新：在 `versions/<ver>/` 下为本轮任务创建新的版本目录
- 创建 `versions/<ver>/规划需求.md`、`更新日志.md`
- 规划对应的 `qa/versions/<ver>/QA-审计报告.md`

### B.3 审计报告

Branch B 审计完成后，主会话向用户输出审计摘要：
- 项目技术栈和结构
- 文档完整度评估
- 代码质量速览
- 发现的问题（文档脱节、架构风险等）
- 下一步计划

### B.4 完成后

Branch B 完成后，`docs/` 已规范化，进入 **Phase 1**（[`01-task-decomposition.md`](./01-task-decomposition.md)）基于当前任务和 `03-开发任务清单.md` 拆分任务 DAG。

## 写作口径要求

无论是 Branch A 还是 Branch B，文档写作遵循：
- 先边界，后细节
- 先 MVP，后扩展
- 先主流程，后边缘能力
- 先用户可感知行为，后实现细节
- 先可执行任务，后抽象愿景

避免：需求文档写成产品宣传；页面文档只写"有个按钮"不写状态和行为；技术设计只有技术栈没有模块职责和数据流；开发任务清单只有一句话任务名没有依赖和验收；把未来构想混进 MVP 导致范围失控。

## 何时不要过度发挥

以下情况下不要擅自加复杂文档：
- 用户明确说"可以适当简化"
- 用户是个人项目或小团队项目
- 用户只是想尽快开始实现
- 用户没有要求测试计划、发布计划、运维体系

这时宁可把核心文档写扎实，也不要额外增加很多低使用率文档。

## Phase 0 完成检查清单

在进入 Phase 1 前，逐项确认：

- [ ] 仓库状态已判定（空 / 非空 / 文档-only）
- [ ] 空仓库 → `docs/` 文档体系已建立（至少 00-03 四份核心文档 + 04 版本标准）
- [ ] 非空仓库 → 已完成审计，`docs/` 已规范化或补全
- [ ] `README.md` 已存在且反映项目真实状态
- [ ] `versions/<ver>/` 已为本轮任务创建版本目录
- [ ] `versions/<ver>/更新日志.md` 与 `handoff/TASK-BOARD.md`（即将创建）状态口径一致
- [ ] `qa/versions/<ver>/` 路径已规划（审计报告在 Phase 8 生成）
- [ ] 文档之间无术语或范围冲突

## 禁止行为

- 跳过 Phase 0 直接拆任务
- 空仓库不建文档体系就开工
- 非空仓库不审计就基于对话记忆写文档
- 文档描述比代码更乐观（写"已完成"但实际未实现）
- 文档描述比代码更悲观（写"待启动"但实际代码已大量存在）
- 引入用户未要求的重流程文档（PRD、概要设计、运维手册等）
